# Caveat rules (EV-02)

Module: `api/caveats.py`, tested by `api/tests/test_caveats.py`. It turns values already sampled at one pixel of the 10 m EPSG:32610 analysis grid into the `caveats` array of the [inspect-point schema](../../contracts/schemas/inspect-point.schema.json). The rules are deterministic and documented here. Nothing is generated by an LLM, and nothing is recomputed: every input is an existing L2 product.

A caveat says that something other than fire can explain, distort or blur the **observed radar change** at a pixel. A caveat that fires does not mean the change is false, and the absence of caveats does not confirm fire, burned area or severity.

The module is a pure function. It changes no contract. `api/raster.py` wires it into `GET /api/inspect/point`: for a valid pixel it samples `slope.tif` and `layover_shadow.tif` (only when `export.json` records `terrain.json`; otherwise both are unknown), `perimeter_edge.tif`, and reads `weather.json` only when `export.json` lists it in `outputs` with a matching sha256. A tampered or malformed `weather.json`, or an out-of-range input, is a 503, never a silent fallback to the generic cautions.

## Inputs

| Input | Source product | Unknown when |
| --- | --- | --- |
| `valid` | DT-02 `valid_mask.tif` | — |
| `slope_deg` | DT-05 `slope.tif` (Horn slope, 0–90°) | `None` or NaN |
| `layover_shadow` | DT-05 `layover_shadow.tif` (0 none, 1 layover, 2 shadow) | `None` or 255 |
| `near_perimeter_edge` | DT-03 `perimeter_edge.tif` (centre within 50 m of the boundary) | `None` |
| `weather` | DT-06 `weather.json`: `period.end` (t2 date), `last_rain_before_t2`, `data_status` | `None`, or `last_rain_before_t2` absent |

An unknown input never fires a rule. An out-of-range value (a slope outside 0–90°, a layover code other than 0/1/2/255, rain on or after t2) raises `ValueError` instead of being silently ignored, because it means a wrong product or a sampling bug.

## Rules

Items are returned in the order of the contract enum. An **invalid radar pixel returns `[]`**, as in the `inspect-point-invalid.json` fixture: there is no radar value to qualify.

| Caveat id | Fires (`triggered: true`) when | Otherwise |
| --- | --- | --- |
| `steep_slope` | slope **> 30°** (strictly) | not listed |
| `radar_shadow_layover` | code 1 (layover) or 2 (shadow) | code 0: not listed; unknown: listed with `triggered: false`, reason "geometry unknown" |
| `soil_moisture_change` | the last AOI-mean day > 1 mm fell **1–7 days** before the t2 date | always listed as a caution with `triggered: false` (see below) |
| `vegetation_structure` | never (no per-pixel rule yet) | always listed as the generic caution |
| `near_perimeter_edge` | pixel in the 50 m band | not listed |

`reason` states the rule and the value, for example `slope 34.2° > 30°`. The slope is shown with the fewest decimals, from one up to six, whose shown value is still strictly greater than 30° (34.24° is shown as `34.2°`, 30.01° as `30.01°`, never `30.0° > 30°`). A slope even closer to the threshold, such as 30.0000001°, reads `slope just above 30°` instead of a rounded number.

### Soil moisture

`weather.json` is an **AOI-wide** daily mean, so this caveat is the same for every pixel and the reason always says it is not per-pixel moisture. DT-06 defines `last_rain_before_t2` as the last day > 1 mm strictly before the t2 date; the t2 day itself is excluded because its rain fell almost entirely after the after scene.

- `weather` unknown: the exact generic caution of the contract fixtures.
- No rain day before t2: generic caution plus "no day > 1 mm before the after scene".
- Rain 1–7 days before t2: fires, with the date and the number of days.
- Rain 8 or more days before t2: generic caution plus the date and the number of days.
- `data_status: mock` adds "MOCK weather data." to the reason.

The 7-day window was proposed in the EV-02 description and accepted by the task owner before approval. It is a documented convention, not a calibrated soil-drying time: L-band sensitivity to moisture depends on soil, canopy, fog and terrain, and daily totals cannot resolve rain within hours of an acquisition (see [weather](weather.md)).

### Generic cautions

`vegetation_structure` and the non-triggered `soil_moisture_change` keep the labels and wording of the contract fixtures (`inspect-point-inside.json`, `inspect-point-outside.json`). A benign valid pixel without weather data returns exactly the fixture caveats.

## Thresholds

| Constant | Value | Origin |
| --- | --- | --- |
| `SLOPE_THRESHOLD_DEG` | 30° | EV-02 description |
| `RAIN_WINDOW_DAYS` | 7 days | EV-02 description (proposed, accepted with the task) |
| `RAIN_DAY_MM` | 1 mm | DT-06 rain-day rule (used in wording only) |
| `EDGE_BAND_M` | 50 m | DT-03 edge band (used in wording only) |

## Expected behaviour on Plaskett

These shares come from the DT-05 and DT-06 runs, not from running these rules on the real rasters:

- 14.4 % of crop pixels have a slope > 30°, so `steep_slope` will be common on the steep coastal terrain. Slopes come from ~30 m GLO-30 data interpolated to 10 m and are smoothed compared with real hillsides.
- 2,858 pixels (0.09 %) are layover and none is shadow. The flags are local and approximate: they miss shadow cast by distant ridges and passive layover.
- The AOI was essentially dry between the acquisitions, so `soil_moisture_change` is expected to stay a non-triggered caution.

## Limitations

- `low_backscatter` and `other_disturbance` are in the contract enum but not implemented: they need a scientific threshold decision first.
- Zone fractions for `review_zones.geojson` are computed by XP-04 with the same slope, layover/shadow and edge-band rules and thresholds ([review zones](review-zones.md)); `pipeline/review_zones.py` mirrors them rather than importing `api/`.
- The 30° and 7-day thresholds are conventions for a visible caution, not tested against radar error rates.
